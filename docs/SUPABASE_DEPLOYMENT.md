# قاعدة Petra على Supabase

## الحالة الفعلية — 2026-10-22

- المؤسسة التي اختارها المالك: `pet`؛ خطة Free، عرض إنشاء المشروع 0 دولار شهرياً.
- [لوحة قاعدة Petra](https://supabase.com/dashboard/project/yzvcinbdeoffygmtptxi)، منطقة `eu-central-1`، الحالة `ACTIVE_HEALTHY`.
- مخطط `petra` خاص: 44 migration أصلية متحققة البصمات، 141 جدولاً مع RLS. لا بيانات مستخدمين أو حسابات إدارة تلقائية، ولا جداول تطبيق في `public`.
- لا خادم موقع بعد: Railway يرفض إنشاء المشروع برسالة `Deploys have been paused due to an upstream issue`. القاعدة مجهزة، ولم يُربط بها API منشور.

## حدود الوصول

يستمر الموقع باستخدام Better Auth وNestJS، ولا يحتاج Supabase API key في المتصفح. لا تعرض مخطط `petra` عبر إعدادات Data API. دورا `anon` و`authenticated` لا يملكان USAGE على المخطط ولا صلاحيات على جداوله أو دواله.

`petra_migrator` يملك المخطط، و`petra_runtime` يملك عمليات بيانات التطبيق والدوال اللازمة فقط. لا يمنح دور التشغيل DDL أو تعديل سجل migrations أو تجاوز RLS. السياسات تسمح لدور الخادم الموثوق؛ صلاحيات الشخصيات والعيادات والموارد تظل مسؤولية API. الدوران حالياً `NOLOGIN`، ولم تنشأ كلمات مرور تشغيل أثناء تجهيز القاعدة.

فحص advisors الأمني فارغ، واختبار SQL متراجع تحقق من عمل trigger الهوية وثبات سجل التدقيق ورفض الوصول من أدوار المتصفح ورفض DDL وتعديل migrations من دور التشغيل. الاختبار محفوظ في `infra/database/supabase/verify-empty.sql` ويشغّل بحساب المشغل مباشرة بعد bootstrap وقبل إضافة مستخدمين فعليين؛ لا تشغّله على قاعدة مستخدمة. الاختبار لا يثبت اتصال NestJS المنشور أو TLS أو SMTP أو Redis أو النسخ الاحتياطي.

## إعادة إنشاء قاعدة فارغة

يسبق التنفيذ فحص القاعدة والتأكد من خلوها ومن اختيار مؤسسة وتكلفة مناسبة. لا تشغّل bootstrap على المشروع المجهز بالفعل؛ إنشاء الأدوار والمخطط متعمد أن يفشل عند وجودها.

```bash
node scripts/supabase-bootstrap.mjs > /path/outside-repository/bootstrap.sql
```

الأداة تولد SQL دون اتصال أو أسرار. طبّق المخرجات بمعاملة واحدة عبر أداة Supabase `apply_migration` أو عميل PostgreSQL موثوق يدعم single transaction. تتضمن تهيئة `btree_gist` في `extensions`، والأدوار والمخطط، ومحتوى migrations الأصلي وبصماته، ثم ملف hardening. SQL لا ينشئ بيانات تجريبية أو حسابات دخول.

## الربط عند توفر الاستضافة

1. أنشئ API والويب والعامل وRedis والتخزين الخاص والفاحص وفق البيئة المعتمدة. لا تتجاوز شروط هوية الإنتاج أو تفعل وضع العرض المحلي على نطاق عام.
2. فعّل LOGIN للدورين بكلمتي مرور عشوائيتين مستقلتين في قناة أسرار المشغل، وامنح قاعدة التطبيق CONNECT عند الحاجة. ضع بيانات migration في مهمة الصيانة فقط، وبيانات runtime في API والعامل فقط. لا ترسل بيانات الاتصال في المحادثة أو Git.
3. خذ وجهة الاتصال الفعلية وشهادة CA من لوحة Supabase. استخدم اتصالاً مباشراً أو Session Pooler، مع `sslmode=verify-full` وشهادة موثوقة؛ لا تخمن اسم pooler أو تضف `rejectUnauthorized=false`. Transaction Pooler غير مناسب لاتصال `LISTEN petra_social_realtime` الحالي.
4. تحقق من `current_user` و`current_schema()` و`search_path` عبر **تسجيل دخول فعلي لكل دور**؛ يجب أن تحل الجداول غير المؤهلة إلى `petra`. اختبارات `SET ROLE` السابقة تضبط المسار صراحة، ولا تثبت أن pooler يطبق إعدادات الدور الافتراضية.
5. تحقق من الصحة والجاهزية وتسجيل الدخول والبريد وWebSocket ورفض الطلبات المجهولة وحماية الملفات عبر HTTPS الفعلي قبل إعطاء رابط موقع للمالك. خذ نسخة خاصة واختبر استرجاعها؛ Free لا يثبت توفر خدمة دائم أو خطة نسخ معتمدة.

للترحيلات اللاحقة احتفظ بمخطط `petra` وسجل `petra.schema_migrations` وبصماته. شغّل `infra/database/supabase/hardening.sql` كمالك المخطط داخل معاملة الترحيلات نفسها بعد إضافة الجداول/الدوال؛ أداة `scripts/production-migrate.mjs` الحالية لا تضيف هذه الخطوة تلقائياً، ولذلك تحتاج تغليفاً أو تحديثاً واختباراً قبل أي ترحيل Supabase لاحق. لا تعدل ملفات migration القديمة أو تضف جداول إلى `public` لإصلاح أخطاء مسار البحث.
