# تقدم Petra — المرحلة 02 — 2026-10-21

## النتيجة الحالية

**أسس مركز الرعاية تعمل ببيانات محفوظة، وبوابة المالك→الحيوان→الحجز→الطبيب→الزيارة الموقعة→المتابعة اجتازت محليًا.** طلب المالك «اكمل» أجاز الانتقال من الهوية. تقريري المرحلتين السابقتين محفوظان في [PHASE00_REPORT](docs/PHASE00_REPORT.md) و[PHASE01_REPORT](docs/PHASE01_REPORT.md).

هذه شريحة تأسيسية من متطلبات الوثيقة 03، وليست استكمالًا لكل توسعاتها أو جاهزية إنتاج. المرفقات الخاصة ونقل الملكية والجدولة المتقدمة والإشعارات الخارجية وبقية الحدود موثقة في [KNOWN_ISSUES](KNOWN_ISSUES.md). التجارة والدفتر والنقل لم تبدأ مراحلها التشغيلية.

## التنفيذ المحفوظ

- `/care` و`/care/pets/:id`: إنشاء الحيوان وتعديل ملفه بإصدار، نوع/سلالة/جنس/لون/وزن/ميلاد تقديري/تعقيم/شريحة/حساسية/حالات مزمنة/اتصال طوارئ خاص. أرشفة بدل حذف السجلات.
- أوصياء بحسابات موثقة وصلاحيات profile/medical/booking مستقلة. المالك وحده يشارك الصلاحيات ويمنح الموافقة العلاجية. وصي الملف الأساسي لا يرى المرض أو الزيارات أو المهام؛ السحب يمنع الطلب التالي.
- موافقة محددة للحيوان والعيادة والطبيب، بانتهاء أقصاه 90 يومًا. الطبيب يحتاج أيضًا اعتمادًا مهنيًا وانتسابًا وdoctor_member في عيادة معتمدة وموعدًا مسندًا. الإدارة أو عضوية العيادة لا تمنح قراءة طبية.
- تدقيق كل قراءة طبية بمرجع الحيوان والفاعل والعيادة دون نسخ نصوص طبية إلى audit أو outbox. قفل الحيوان يسلسل إلغاء التفويض مع العمليات الطبية.
- مدير العيادة يضيف خدمة ومدتها في `/clinic/:id`؛ الطبيب ينشر وقتًا وفرعًا وخدمة من `/doctor`. التخزين UTC والعرض Asia/Baghdad.
- PostgreSQL يقفل الوقت، ويمنع تداخل الطبيب والحيوان عبر exclusion constraints. قائمة التوفر تخفي الأوقات التي تتداخل مع حجز للطبيب. مفتاح المحاولة يعيد الحجز نفسه ويمنع استعماله لمحتوى مختلف، حتى مع طلبين متزامنين.
- حالات confirmed/completed/cancelled محكومة؛ إلغاء للمالك أو وصي الحجز قبل وجود مسودة. الحجز لا يولد دفعًا أو إيرادًا.
- زيارة SOAP مسودة بإصدار، يراها الطبيب فقط؛ وصفات ولقاحات وفحوص ومتابعات يكتبها الطبيب. لا تشخيص أو جرعات أو جدول لقاح مولد آليًا.
- توقيع بعد بداية الموعد يُكمل الحجز وينشئ المهام وأحداث outbox ضمن المعاملة نفسها. trigger يمنع تعديل/حذف الأصل الموقع. الإضافة موقعة ومستقلة وغير قابلة للتعديل.
- طلب الفحص الموقع يبقى كما هو؛ اعتماد نتيجته اللاحقة مرة واحدة باسم الطبيب ووقت المراجعة ونصها، مع منع إعادة الاعتماد أو تعديل النتيجة المحسومة. التصحيح بإضافة موقعة.
- مهام داخل التطبيق مع المصدر والفاعل والتوقيت: planned/due/completed/skipped. المالك/الوصي الطبي يكمل أو يتجاوز؛ لا ادعاء تسليم بريد أو SMS أو push.
- ملخص طبي خاص قابل للطباعة من المتصفح. لا QR عام أو شهادة/PDF تنظيمي، ولا ظهور لنماذج الوصاية أو الموافقات في الطباعة.
- migrations 0005 للرعاية و0006 للفحوص؛ لم يتغير checksum ملف مطبق. ADR-002 يوثق التفويض والتوقيع ومنع التداخل.

### ما تثبته اختبارات الرعاية

- عزل المالكين والطبيب غير المعالج ومدير العيادة؛ حقول تصعيد الملكية مرفوضة وتعارض نسخة الملف يعيد 409.
- وصاية محدودة ثم كاملة للقراءة الطبية والحجز، ومنع إعادة المشاركة والموافقة من الوصي؛ الإلغاء يمنع القراءة وإلغاء الحجز من الوصي السابق.
- صلاحيات إنشاء الخدمة/نشر الوقت، واعتماد الطبيب وانتسابه؛ الموافقة وحدها لا تفتح ملفًا دون موعد، والموعد دون موافقة لا يفتح السجل.
- سباق شخصين على وقت واحد يفوز به حجز واحد، وسباق مفتاح محاولة واحد يعيد الحجز نفسه. رفض تداخل الطبيب عبر وقتين والحيوان عبر طبيبين، وعدم تكرار حدث التأكيد.
- المسودة لا يراها المالك، وتوقيع موعد مستقبلي مرفوض. سحب الموافقة أو انتهاؤها أو سحب الانتساب يوقف الطلب التالي.
- توقيعان متزامنان ينتجان توقيعًا واحدًا ومهمة واحدة؛ منع تغيير/حذف الأصل على API وDB. الإضافة تحفظ الخطة الأصلية؛ النتيجة تعتمد مرة واحدة وtrigger يحميها.
- رحلة المتصفح الحقيقية: إنشاء حيوان→حجز→موافقة→فتح الطبيب للزيارة→حفظ SOAP ومتابعة→توقيع→قراءة المالك وإكمال المهمة ثم إعادة التحميل.
- فحص overflow بعروض 320/390/768/1440 وaxe على ملف الحيوان ومساحة الطبيب. الصور من بيانات اختبار اصطناعية.

الاختبارات تنشئ قاعدة PostgreSQL مؤقتة وسرًا مؤقتًا وتطبق migrations من الصفر ثم تحذف قاعدة اختبارها فقط. fixtures الرعاية تستخدم مكتبة الهوية الرسمية داخل القاعدة المؤقتة وتجهز الجهات المهنية بوصفها fixture؛ اختبار مسار الاعتماد الحقيقي في identity.spec مستقل. لا تعديل لحدود HTTP أو قاعدة المطور، ولا تمثل أسماء الجهات أو البيانات الطبية اعتمادًا أو علاجًا حقيقيًا.

### إصلاحات قاد إليها التحقق

- شريط مساحة الحساب كان خارج landmarks؛ أضيفت region مسماة واجتاز فحص الوصول الكامل.
- بناء Next لا يحل إعادة تصدير care.js من مصدر TypeScript؛ جُمعت العقود في مدخل الحزمة المشترك مع بقاء imports API متوافقة مع ESM، ونجح البناء.
- التوقيع لا يظهر مع تعديلات مسودة غير محفوظة؛ الحفظ والإصدار مطلوبان قبل توقيع النسخة الحالية.
- قفل اعتماد الطبيب والعيادة والانتساب والعضوية أثناء المعاملة يحد من السباق مع السحب. انتهاء الموافقة وفقد الصلاحية يفحصان في الخادم.
- قائمة الأوقات تستبعد تداخل حجز الطبيب، مع بقاء قيود DB الحاسمة عند الطلب المتزامن.

## البيئة وحالة التسليم

حُفظت مسودة إعداد البيئة بنجاح بتعليمات المرحلة 02 وسكربت التثبيت الكامل المختبر. ربط المستودع حُدّث إلى `mount_path=pet` بعد فحص `/workspace`؛ `/workspace/.git` فارغة وليست checkout أخرى. المستودع `xmohemnx/pet` فعليًا على فرع رمزي unborn دون commit؛ لا ادعاء إمكانية استرجاع الشفرة من Git أو من مهمة سحابية جديدة. نسخة تعليمات البدء القابلة للمراجعة في [CLOUD_START](docs/CLOUD_START.md).

الحفظ لا ينشر المسودة. لتفعيلها، راجع واحفظ التغييرات في إعدادات البيئة ثم انشر البيئة؛ `requires_publish=true`. لم تتغير الشبكة أو متطلبات أسرار خارجية؛ التطوير المحلي لا يحتاج بيانات مزود. لا تُفترض نجاة عمليات Docker أو بيانات volumes بعد snapshot دون اختبار استرجاع مستقل.

الخطوة التالية في البناء: استكمال توسعات الرعاية المذكورة في KNOWN_ISSUES ومراجعة الشريحة قبل دخول تجارة العيادة في المرحلة 03 وفق roadmap. الباقات والمحادثة الطبية والفندق ضمن المرحلة 05، والمالية تسبق معالجة أي مال فعلي.
