# ADR 029 — PostgreSQL خاص على Supabase للنشر المؤقت

الحالة: بطلب المالك بتاريخ 2026-10-22، داخل مؤسسة Supabase المختارة `pet`.

## القرار

يستخدم Petra قاعدة PostgreSQL المدارة من Supabase مع NestJS وBetter Auth الحاليين. لا ننقل الهوية إلى Supabase Auth ولا نضع مفاتيح قاعدة أو service-role في المتصفح. جداول التطبيق في مخطط `petra` خاص خارج Data API؛ لا يمنح المخطط أو جداوله أو دواله أي وصول إلى `PUBLIC` أو `anon` أو `authenticated`.

ينشئ المشغل دورَي `petra_migrator` و`petra_runtime` بلا تسجيل دخول مبدئياً. الأول يملك مخطط التطبيق؛ الثاني يملك DML ودوال التطبيق فقط، ولا يملك إنشاء أو حذف الجداول أو تعديل سجل migrations. يمنح حساب مشغل القاعدة القدرة على `SET ROLE` لاختبار الدورين؛ لا يرث صلاحيات التشغيل تلقائياً من عضويته في `petra_runtime`. يضبط مسار البحث إلى `petra, extensions` للدورين والدوال، وتبقى الإضافات في `extensions`. تفعّل RLS على كل جدول؛ سياسات التشغيل تسمح لدور الخادم الموثوق، وتبقى صلاحيات المستخدم والعيادة والموارد في API كما هي. هذه ليست سياسات تعتمد على `auth.uid()` ولا ادعاء بعزل المستأجرين داخل PostgreSQL.

يولد `scripts/supabase-bootstrap.mjs` SQL لإنشاء جديد فقط من ملفات migrations الأصلية مع بصمات SHA-256 نفسها. يطبق المشغل المخرجات في معاملة واحدة، ولا يغير migrations القديمة ولا ينشئ seed أو مديراً. بعد أي migration مستقبلية يشغّل `infra/database/supabase/hardening.sql` في المعاملة نفسها لإعادة منح الصلاحيات المحددة وتفعيل RLS للدخل الجديد.

## الربط وحدود النشر

بيانات الدخول تنشأ وتحقن في مدير أسرار الاستضافة عند توفر الخادم. لا يفعّل تسجيل دخول الدورين أثناء التجهيز وحده. تستخدم اتصالات TLS مع التحقق من الشهادة واسم المضيف، باتصال مباشر أو Session Pooler؛ Transaction Pooler غير مناسب لاتصال `LISTEN` الاجتماعي. يجب اختبار مسار البحث للدورين باتصال فعلي قبل تشغيل API؛ لا يعادل `SET ROLE` اختبار تسجيل دخول أو TLS أو سلوك pooler.

تعليق Railway لعمليات النشر حالياً عائق خارجي. إنشاء قاعدة سليمة وتطبيق مخططها لا يعني أن الموقع منشور أو أن الخادم مرتبط بها. تبقى بوابات الإنتاج والخدمات المالية الخارجية مغلقة، والبريد وRedis والتخزين وفحص الوسائط والنسخ الاحتياطي متطلبات مستقلة.
